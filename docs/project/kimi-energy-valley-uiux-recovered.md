## 第一部分 · 项目理解（阅读笔记）

### 1.1 这个项目是什么

MoonTown 是一个 **MoonBit 原生的小镇级编排控制面（town control plane）**，架构分三层：

1. **内核（src/ 各包）**：调度（dispatch）、存储（storage）、健康（health）、调度器（scheduler）、角色（roles/Mayor）等，把多个 moonbook 知识域和多个 moonclaw 运行时编排成一个"小镇"。
2. **地图契约**：早期版本用固定坐标场景投射镇况；当前版本已由 `energy_valley_contract` 的编译世界与快照取代。
3. **浏览器前端（src/ui/rabbita-town）**：用 **Rabbita**（MoonBit 的 Elm 架构前端框架，`moonbit-community/rabbita@0.12.4`）写的单页应用，编译目标为 JS，不使用 npm/Vite/React——`scripts/build-rabbita-ui.sh` 完成 fmt → check → info → build(js,release) → 静态组装 → 校验，产物在 `dist/`。

前端的软件架构非常规整，是典型的 **TEA（The Elm Architecture）**：

- `main/types.mbt`：全局 `Model`（约 60 个字段）与 `Msg` 枚举（约 50 个消息）。
- `main/app_lifecycle.mbt`：`update` 函数按消息分支返回 `(Cmd, Model)`。
- `main/energy_valley_page.mbt`：`render_energy_valley_page` 组合规范语义页面——底层一张 `<canvas>`（等距视角小镇地图），上面浮层：左上角镇徽 + 天气，右上角指标条 + 看板，左下角事件流，右侧建筑检视器，底部工具坞（视察/铺路/造林/拆除/四种建筑），右下角指南与重置。
- `main/energy_valley_canvas.mbt`（2300+ 行）：Canvas 2D 等距渲染管线——地形 → 道路覆盖层 → 按深度排序的树/Agent/建筑 → 天气 → 昼夜。相机支持拖拽平移、滚轮缩放，道路/公园支持笔刷涂抹。
- `main/exact_energy_valley_world.mbt`：世界生成器，是 **256×144 温榆河语义参考图（真实昌平未来科学城·能源谷总平面图栅格）** 的适配层——地形来自人工标注的参考标签（`wenyu_reference_labels.json`）+ 程序化语法；道路来自从总平面图提取并连通性修复的路网图（`wenyu_reference_roads.json`，M=主干道，R=普通路，b=桥）。

**关键判断**：这个前端本质上是一个"小镇模拟器皮肤"，真实工作（runtime）接进来时 Agent 会真实移动干活；没接时是演示模式。UI 的中文文案、无障碍（aria-label、快捷键 1–8/空格/Esc）、降级（prefers-reduced-motion）都做得相当专业。

### 1.2 现状的真实短板（以一个完全的新手视角体验后的结论）

我把一个"第一次打开这个页面的人"会问的问题列出来，对照现状回答：

| 新手的问题 | 现状 | 评价 |
|---|---|---|
| **我是谁？我能创建自己的角色吗？** | 不能。页面上没有"我"，只有 12 个演示居民和真实运行时 Agent | ❌ 最大缺口。小镇游戏没有"我"就没有代入感 |
| **我怎么操控我的角色？** | 只能拖相机、点建筑看详情，没有任何可操控实体 | ❌ 第二缺口 |
| **我怎么和别的角色聊天？** | 完全没有聊天/社交界面。Agent 只是地图上的移动点 | ❌ 用户明确想要的"虚拟手机"不存在 |
| **我怎么逛各个大楼？** | 点建筑有检视器（真实任务/Agent/Run ID），建筑有程序化内部（procedural interiors）但入口深、纯信息向 | ⚠️ 有基础但不像"逛"，像"查台账" |
| **我怎么产出新知识（新大楼）？** | 底部工具坞可花预算建 4 种楼（研发塔楼/实验室/工坊/人才公寓），但"建楼=产出知识"的心智没有打通，建完没有庆祝、没有内容沉淀 | ⚠️ 动作在，意义感不在 |
| **怎么发布分享、收藏别人的楼？** | 完全没有发布/分享/收藏概念 | ❌ 缺口 |
| **玩下去的动力是什么？** | 没有任务、没有等级、没有奖励、没有目标 | ❌ 一次性玩具风险 |
| **管理者看什么？** | 有一个"看板"按钮（energy_board），内容是运行指标；运营视角（增长、活跃、转化）完全没有 | ⚠️ 有运行看板，没有运营看板 |

### 1.3 美术诊断（对照 AGI小镇 agitown.com.cn 与 a16z ai-town）

参考对象观察：

- **AGI小镇（agitown.com.cn）**：以"AI 居民"为绝对主角——每个居民有名字、身份（科技部长/经济部长/法师）、创作者归属，内容围绕居民的故事与社交展开。氛围温暖、人格化。
- **a16z ai-town**：16×16 像素风、PixiJS、暖色草地 + 木屋 + 角色对话气泡，观感"可爱、松弛、有人气"。

对照之下，能源谷前端的美术问题：

1. **色调过冷过暗**：整体 `bg-slate-950` 深海军蓝 + 琥珀点缀，像"运维监控台"，不像"小镇"。ai-town 的愉悦感来自高明度的草地绿、木色、暖光。
2. **地图是"规划图"不是"小镇"**：256×144 的规划栅格直接可视化，地块大、空、重复；道路是规划级路网，缺少生活细节（路灯、长椅、行道树、广场铺装、水岸栈道）。
3. **没有地标**：真实能源谷最重要的现代地标——**地铁 17 号线（未来科学城站、未来科学城北站，2023 年底开通，贯穿能源谷核心区）**——地图上完全没有。温榆河水系在，但滨水公园（现实中 314 公顷的滨水公园）没有表达。
4. **居民没有"人气"**：演示居民只有 12 个、无名无姓、不会说话、头顶只有工作状态符号。AGI小镇证明"有名字有身份的居民"是吸引力核心。
5. **建筑美学单一**：程序化等距盒子 + 窗户，风格偏"示意"。需要风格化处理（屋顶花园、玻璃幕墙渐变、夜景亮灯）但不能脱离真实总平面图——**用户明确要求：保留昌平未来科学城能源谷的地图大概、修正道路、加细节、风格化但不重构**。

## 第二部分 · 优化总纲

### 设计原则

1. **先有"我"，再有镇**：一切从创建角色开始，角色是玩家在镇上的具身。
2. **最小学习成本**：每个用户旅程三步以内完成核心动作；所有功能从地图上的"看得见的入口"进入，而不是藏在菜单里。
3. **动作必有回响**：每个动作立即给出视觉/奖励反馈（toast、星光、动画），并挂接任务链。
4. **共建优先**：所有游戏化系统都指向"和别人一起把镇建得更好"，而非单机刷分。
5. **美术服务于人气**：一切视觉调整以"温暖、有人气、有地标"为目标，地理骨架不动。

### 实现真实性边界

- 离线居民聊天是确定性的本地角色剧本，不冒充 AI 或真实 runtime 通讯。
- runtime Agent 联系人展示真实投影中的任务、状态与 Run ID；当前后端没有“给 Agent 发自由文本消息”的接口，因此手机把用户送入已有的真实工作请求流程，不伪造发送成功。
- 运营中心只统计本浏览器持久化事件和当前 runtime 投影；广告位、人才市场与公司展示均明确标记为演示目录，不计入运营指标。
- 分享优先使用 Web Share API，回退到剪贴板；接收方通过 URL 参数恢复分享卡，并可把收藏建筑落到符合温榆路网可达性规则的真实地块。

### 2026-08-06 验收补记

- 角色编辑入口、三步语义与无障碍标题已修复；不可用的继续按钮使用真实 `disabled` 语义。
- 行走任务只会在角色实际走过两格或抵达更短目的地后完成；最后接受的道路目的地跨刷新保留。
- 未填写主题的知识楼保存为空草稿，并可从广场继续；拆除或重置地图会清理对应的本地实体记录，避免孤儿卡片。
- 运行成果分成已完成、待审核、进行中、失败四类；只有已完成且有可核验证据的成果能收藏成楼。
- 分享网址只保留 `seed` 与显式分享字段，不携带面板、启动、令牌或其他无关查询参数；系统分享的取消/失败不会被文案误报成已完成。
- 手机中的过期和断开 Agent 不再显示为“工作中”；真实工作请求会携带所选 Agent、当前任务和 Run 上下文，但最终执行者仍由调度策略决定。
- 运营事件现在即时持久化，自动日报按刚结束的游戏日统计；运行看板、建筑检视器与其他覆盖层保持互斥。
- 手机、广场、任务、工具、地铁图例和反馈提示在桌面、竖屏手机、矮屏横屏及安全区设备上有独立布局；地铁线路位于地物下方，车站和出入口地标位于建筑上方。
