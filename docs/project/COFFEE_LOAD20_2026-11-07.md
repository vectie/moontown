# 半醒咖啡 · 20 人并发实测

2026-11-07，北京时间。结论：**20 张真实图片全部生成，但状态轮询和图片交付出现异常，本轮不能判为全链路通过。**

## 场景与边界

- 20 个新建、真实登录的普通账户，没有增加平台角色。准备账户与登录不计入生成等待。
- 20 个客户端在 2ms 内同时发起生成；请求重叠峰值确为 20。每人限 1 张，全场严格 20 张，未重复提交推理。
- 使用独立 `moontown-coffee-load20` 实例、配置与 PVC，复制正式首期的原生镜像、静态资源、CPU/512Mi 内存限制和网络规则。
  原生摘要 `62213c1b…`，UI `4914aeaf…`。请求经过真实外网 HTTPS :8443、统一登录、175 图像适配器及 177 ComfyUI。
- 覆盖正式首期的 `api/creative` 单活动生成链路；不代表 20 台手机渲染、20 个主办创建 MoonBook，或动态活动的全量性能验收。
- 模拟 20 个会话每轮完成后间隔 4 秒继续查状态，完成较早的用户也持续查询。
  同时读取正式活动公共 API；没有正式投稿、选票或出图请求。
- 页面 HTML/JS/CSS 单独取样；不是浏览器完整页面加载时间。客户端耗时包含 curl 进程启动，约数十毫秒。

因此 20 人实际是排队，不能据此宣传为 20 路同时出图。每张约 8.6 秒再加消费者调度间隔，
使最后一人的可见等待达到约 3 分 24 秒。

## 页面/API 与异常

| 客户端单次请求 | 样本 | 中位数 | P95（包含错误响应） |
| --- | ---: | ---: | ---: |
| HTML | 20 | 202ms | 222ms |
| JS | 20 | 182ms | 232ms |
| CSS | 20 | 174ms | 313ms |
| 已登录首次状态读取 | 20 | 2.59s | 2.61s |
| 提交生成 | 20 | 2.59s | 3.48s |
| 状态轮询 | 620 | 2.54s | 3.68s |
| 正式活动公共 API 探针 | 31 | 176ms | 323ms |

主场景共记录 751 次请求，其中 **40 次状态轮询返回 503**：620 次轮询的 6.45%，
集中在两个各 20 请求的轮次，耗时约 3.66–3.77 秒。后续轮询自行恢复，20 张图均完成。
正式活动公共探针 31/31 成功。

代码中普通状态查询每次重新读取统一会话和账户资料，不跨请求缓存已完成的授权。
`account_identity` 使用 3500ms 校验上限；这与错误波次的时长和该路由的
`identity_unavailable` 分支相符。认证链路是明确的优先排查点，但没有进一步证明
是 TLS、DNS、SSO 后端还是生成过程中的调度停顿；本报告不把推断写成已定位的根因。
推理结束后，仅重放 4 轮 × 20 个认证状态读取，80/80 成功，没有额外出图。

首轮 20 路图片下载中，19 份文件与服务端摘要一致，用户 17 的文件只有 92,421 字节且摘要不符。
早期压测脚本在首个失败时终止，未持久化全部下载状态，因此无法精确区分原始传输错误与取消影响。
随后只重测下载，**20/20 HTTP 200 且摘要全部一致**，P95 3.65 秒，最长 3.77 秒。
没有重新生成图片；首轮交付异常保留为失败证据，不能用复测结果覆盖。
脚本已改为先保存完整请求与校验记录，再决定失败，并为非 200/非零退出保存错误证据。

## 判断与下一步

20 人能完成一次生成，计算链路具有可用的串行吞吐；目前不适合宣传为“20 人同时秒出”。
建议先消除认证状态查询的 503，分解校验耗时并检查连接复用/受信内部路径，保留撤权实时性；
不要通过缓存已完成的授权或单纯延长超时掩盖问题。随后再评估抖动轮询与可见的排队位置/预计等待。
单实例生成并发是否能提高，需要单独实测显存与同机 Qwen 延迟，本次没有调大。
