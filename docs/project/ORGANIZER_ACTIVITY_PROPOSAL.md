# 主办方申请与活动落地方案

状态：2026-11-07 提案。活动级定向管理权限已用于手机验收；本文件描述的申请审批、
落地表单、自动发布和统一运营台尚未全部实现，不能视为已开放的能力。

主张：批准一个具体活动方案及其资源范围，再把有边界的落地工具交给申请人。
平台账户、某场活动主办、平台管理员是三个不同层次。注册不获得主办资格；
主办也不获得 PlatformOperator、集群管理或其他活动的访问权。

## 三个人各自怎么用

### 申请主办的人

从「申请举办」提交企划，可上传现有材料或引用一本自己有权访问的 MoonBook。
只收集五组决策：活动目的与受众、主题和作品形式、时间与人数、奖品及承担方、
需要平台提供的模型/算力及额度。联系方式只供审批人看，不进入公开活动页。

提交后看到「待审核 / 需补充 / 已批准 / 不予批准」和具体意见，修改后保留版本。
没有通过审批的人可以保存企划草稿，不能发布活动、启动付费任务或调用活动预算。

通过后收到「活动落地书」：已带入批准的方案、资源上限和可用模板。
主办填写主题文案、品牌参考、投稿规则、评选方式、奖品和发奖说明，检查手机预览，
点击「生成活动」。不需要抄写 ID、填写集群 IP 或自己配 ComfyUI。

### 平台所有者（当前是 kq）

审批页集中看企划、申请人、风险与交付责任、现金和算力预算。
一次批准中明确：哪位主办、哪一场或几期活动、可用模板及模型、有效期、
单人/全场额度、并发、允许的奖品文案及评选方式，以及是否可在批准范围内自行发布。

「批准」产生活动级授权包，不是修改全局账户角色。
预算不足、超期或资源不就绪时，活动留在草稿/待处理状态，给出原因。
提高额度、更换模型、扩大活动次数、改变已公布的评选规则，需要重新提交变更。
可暂停生成、撤销主办授权、接管活动；保留操作日志与撤销前后的版本。

### 参与者和观众

手机打开活动 → 页内登录 → 编辑提示词 → 生成私人草稿 → 明确确认公开投稿。
审核通过才进入作品墙；退回意见显示在作品旁，可修改后重新提交。
每期一张有效作品，新版重新审核。主办自己的参赛作品必须由另一位受权审核人处理。

观众看到明确的投票开始/结束时间与计票规则。外部腾讯文档投票由腾讯承接计票，
MoonTown 保存关票时的参赛作品版本和外部结果快照，不伪造站内实时票数。
如果需要站内实时投票，必须单独实现投票身份、重复票限制、撤回/刷票处理和结算快照。
演示入口永远显示「不计票」，不能作为真实投票验收通过的证据。

## 与现有概念对应

| 现有概念 | 这里承担的职责 | 需要补的连接 |
| --- | --- | --- |
| 统一账户 | 真实登录身份 | 申请人与活动级授权关系，不提升全局角色 |
| Contest Express / Challenge | 公开主题、scope、可能性 wiki、第一人称玩法、赛程和材料 | 从批准的活动落地书生成 Challenge 和活动实例 |
| MoonBook | 策展内容、品牌来源、企划、规则、模板及复盘 | 私有申请材料与公开活动资料分开投影，按期固定版本 |
| MoonClaw curator | 读落地书，整理文案、参考提示词、排期、运营待办和复盘草稿 | 使用平台已批准的策展 profile；不能自己批准企划、增权或加预算 |
| LunaNexa / MoonGate | 模型路由、调用凭据、用量与资源授权 | 一场活动一份预算与授权；凭据只在服务端，按调用记录到活动 |
| ComfyUI | 执行批准的文生图工作流 | 固定工作流版本及模型，主办不直接提交任意节点或服务器指令 |
| creative_contest | 私人生成、投稿、审核、公开作品墙、过审名单 CSV 与开奖记录 | 多活动实例、定向管理人、活动运营入口、固定版本结算和投票适配 |

一场活动拥有一本工作用 MoonBook；每周一期保存独立主题、规则版本、作品名单和结算。
复用策展模板与 profile，不复制共享一份可写的赛事状态、参与者信息或无限算力授权。

## 最少的状态与权限

申请：草稿 → 待审核 → 需补充 / 已批准 / 不予批准。
活动：草稿 → 资源检查 → 可发布 → 征集 → 审核收尾 → 投票 → 已结算 → 归档。
暂停是单独的运行状态，保留可恢复的数据；终止不等于删除作品和审计记录。

授权包至少记录申请版本、activity_id、组织者账户、审核人/协作者、权限集合、
资源策略版本、起止时间、预算和批准者。每次服务端操作校验当前授权与活动 ID；
撤销后已登录的 cookie 也不能继续管理。前端隐藏按钮只是呈现，不是权限校验。

建议预设权限为：编辑本活动草稿、在批准范围内发布、审核投稿、维护投票入口、
导出本活动名单、记录/公布结果、查看本活动用量。协作者可以只授予审核权。
禁止查看未投稿的私人作品；禁止修改其他活动、平台账户角色、服务凭据和集群设置。

## 「生成活动」实际做什么

1. 校验批准方案版本、主办身份、模板、预算与赛程，展示最终公开预览。
2. 创建活动实例和独立存储；固化 MoonBook 的公开内容、来源和规则快照。
3. 绑定 curator profile、批准的 ComfyUI 工作流和活动算力预算。
4. 生成参与页、审核入口、作品墙及投票适配；检查登录、模型路由和存储是否就绪。
5. 范围未越过批准包且允许自行发布时，发布活动；否则生成待审批预览。

同一次点击必须有幂等键；部分失败保留进度并可重试，不能报「创建成功」后留下
没有算力或没有审核入口的活动。未发布活动不接受公开投稿，不预先消耗出图额度。

## 主办方活动管理页

手机顶部只展示「当前阶段、下一件待办、待审核数量、剩余额度」。
主要区块为作品审核、活动设置、投票/结果、资源与复盘。
常用操作就近展示：批准/退回及意见；修改公开信息并预览；关票导出；记录奖项。
每次批量批准、换规则、公布结果等有后果的动作，展示影响范围后再执行。
原始任务 ID、模型诊断和审核审计放在高级详情中。

现金预算与算力预算分别展示：每月 1000 元运营费并不自动等于可花费 1000 元算力。
已有算力也要记录占用时间/请求上限，并优先保障正在运行的文本服务。
每周活动的自动排期沿用同一批准包的有限次数，不能无限续期或自动采购奖品。

## 建议实施顺序

1. 完成真实三方手机验收，补页内登录、退回再投、定向管理与投票状态反馈。
2. 企划申请 + kq 审批 + 活动级授权包 + 可预览的落地书，先支持咖啡创作模板。
3. 落地书生成多活动实例，接 MoonBook/curator/预算；加主办运营台与失败恢复。
4. 根据活动规模选择真实腾讯文档计票或站内投票，再补周赛复用和复盘归档。

当前只有单一正式咖啡活动的部署配置；不是已经存在的通用多主办 SaaS。
当前 CSV 是当时已过审名单的导出，尚没有服务端固定关票版本、外部票数回传或实时榜。
作品撤回后外部腾讯文档选项不会自动同步，结算时须按作品 ID 校对撤回/失效状态。
应在现有概念上补审批与授权连接，不新造第二套账户、内容库或算力平台。
