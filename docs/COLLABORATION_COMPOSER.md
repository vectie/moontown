# One-off collaboration composer

To explore actual Book text before writing a question, use the
[local material notebook](MATERIAL_NOTEBOOK.md). Import selected files, search
their passages, author observations and independent challenges, and save a
byte-checked new inquiry that opens in this ordinary composer.

The **Challenge a source claim comparison** action accepts an existing claim
comparison JSON report before any participant work has run. Explicitly map the
selected group to registered Book files, author challenges and a falsifier, then
save through the ordinary draft flow. See [Source claim challenges](CLAIM_CHALLENGE.md)
for exact-byte checking, limits and interruption behavior.

The request desk's **Collaboration** action authors a question for two or more
existing Books. Choose the Books, browse/search and select observed source paths
(or enter exact workspace-relative paths), describe each focus, perspective, contribution and next artifact, and
name the human who must review the plan. An optional authored objection has an
explicit human decision owner. No idea or synthesis is generated by this flow.

## Save, reopen, prepare and download

- **Save draft and capture sources** accepts incomplete assignments. Every
  selected source must be an existing regular file in the selected Book. Hidden
  paths, absolute/traversing paths and symlinks are rejected. Catalog reads do not
  provision or normalize Books.
- Saving captures exact binary source bytes and SHA-256 digests. Nested paths
  are retained. A changed field or changed source creates an immutable new
  revision; retrying an unchanged save returns the existing revision. Concurrent
  edits require reopening before they can replace the current pointer.
- **Reopen** verifies the saved revision and its captured files. It does not
  silently substitute newer live Book files. Save again to capture changed live
  source content.
- **Prepare one-off handoff** checks the question, two participant assignments,
  captured sources and named-human review. It writes the existing civic v1
  handoff with an empty `ideas` array, one brief per participant, a frozen source
  packet, and MoonChat's existing v1 conversation review bundle. All decisions
  remain pending. No extra acknowledgment checkbox is required for local
  preparation or download.
- **Download prepared plan package (.tar)** exports a deterministic `.tar`
  containing the manifest, all exact source bytes, briefs, handoff and review
  bundle. Extract it before using the relative references. Individual artifact
  downloads are convenience copies; the complete archive preserves nested
  references and predecessor review evidence. The archive has no machine roots
  added by the host.
- **Reuse saved question as a fresh draft** requires a new ID and recaptures the
  selected files. It copies authored fields from the exact reopened revision,
  even if another editor has since saved a newer revision. Prepared identities, previous
  review linkage and decision receipts are not inherited.

Current bounds: 16 Books, 16 source files per Book, 1 MiB per source, 8 MiB of
current source bytes, 64 predecessor revisions, 256 listed drafts and 32 MiB of
portable artifact history. Reuse as a new draft when history reaches its bound.
Files and local authoring directories use private permissions. Local storage
and registered Book workspace roots must be absolute and symlink-free.

## Authority and ownership

This is preparation, not an executed collaboration or an accepted Book outcome.
It never invokes civic bootstrap/install, a daemon, a schedule, a provider,
MoonClaw or a participant Book writer. `interval_ms: null` is merely the civic
wire representation: older civic installers can still create a recurring
schedule from it. Do not run an installer to preview this package. Execution and
human settlement are separate, explicitly authorized workflows.

The review bundle binds the exact bytes of its frozen source packet. Town also
verifies every constituent snapshot and generated artifact on preparation retry
and export. A changed revision retains exact predecessor bundle bytes and their
revision-scoped relative references, while starting with no decision receipts.
Reopening a draft does not import or apply later review decisions. Returning a
settled review receipt to Books is outside this feature.

## Source dependency and build layout

This change requires the paired MoonChat source with the new review-authoring
helpers. The registry's existing `vectie/moonchat@0.1.0` is not sufficient by
itself. The shipped root and Rabbita `moon.work` files resolve the paired source
without a private harness override. Arrange both delivered source trees as:

```
workspace/
  moonchat/          # paired review-authoring source
  moontown/         # this source, including its committed moon.work
```

From `moontown`, run `moon check --target native`, then the narrow authoring
tests with `moon test --target native --strip src/collaboration_authoring` and
`moon test --target js src/collaboration_contract`. From
`moontown/src/ui/rabbita-town`, run `moon check --target js` and
`moon test --target js main/collaboration_wbtest.mbt`. Existing CI or standalone
checkouts must check out/replay the paired MoonChat tree at that sibling path.
Do not remove the workspace and silently resolve the older registry package.
A standalone registry release requires publishing the compatible Chat helpers
and updating Town's declared version first; this delivery publishes nothing and
requires no new credentials.

Qualified dependency graph: MoonChat source + async 0.20.2, x 0.4.50, MoonLib
0.1.19, Lepusa 0.1.4; Rabbita UI additionally uses Rabbita 0.14.0. The native
`civic` package is never imported into JS. Cross-target contract/client types
are in `src/collaboration_contract`; all filesystem and civic/Chat authoring is
in `src/collaboration_authoring`; the existing localhost desktop host is a thin
adapter.

## Local API

`POST /api/collaboration` uses the desktop host's existing same-origin,
content-type and bounded-body checks. Routing happens before supervisor or
runtime initialization. The contract is
`moontown.collaboration.request.v1`: `request_id`, `action`, `draft_id`,
`revision`, `new_draft_id`, `artifact_path`, and optional `draft`/`payload`. Actions include
`list`, `source-list`, `save`, `load`, `reuse`, `prepare`, `export`, and `download`.
`source-list` resolves only `payload.book_id` through the registered catalog and
returns the optional `source_listing` observation described below. `revision`
is the expected current revision for save and exact saved revision for reuse,
prepare and downloads. `export` returns tar bytes; `download` requires an artifact path
already present in the prepared revision. Other replies use
`moontown.collaboration.reply.v1` and echo the request identity.

Rabbita drops stale responses after newer form changes, clear, closing the
request desk or switching primary surfaces. An interrupted save may already
exist durably; reopening or retrying the same request resolves that state. A
browser download callback checks the current generation before creating a file.

## Qualification boundary

Native fixture tests consume actual civic and MoonChat decoders, capture binary
sources with NUL/non-UTF-8 bytes, verify nested source paths, deterministic
retries, changed revisions, missing/oversized/symlink sources, snapshot tamper,
reopen/reuse, pending reviews and manifest/brief tamper. Rabbita fixture tests
exercise the real rendered composer, lifecycle and stale callbacks. These are
source/native/UI-fixture checks, not a live browser, Mac, provider or human
decision validation.
## Registered Book source picker

After loading Books, add a participant Book and choose **Browse current sources**.
The Book ID, shown beside its title, identifies the participant even when two
Books have identical names or paths. Search filters the observed relative paths;
it does not search file contents or an unobserved remainder. Select or remove
paths, review the selected paths and assignments, then explicitly choose
**Save draft and capture sources**. Browsing and selecting do not capture bytes,
create draft revisions, execute collaboration work, or write to a Book.

The host's `source-list` collaboration action accepts `payload.book_id` only as
the root selector. It resolves the ID through the existing host-owned catalog;
caller-supplied filesystem roots are never used. It reports up to 256 eligible
files after at most 2,048 directory entries and eight nested directory levels.
Paths are sorted within the observed subset. Hidden/unsafe paths, symlinks,
nonregular files and files over 1 MiB are excluded. Exclusion/unreadable counts,
truncation and incomplete-list explanations remain visible. A file can disappear
or change immediately after observation; this list is not a transactional snapshot.
The existing exact path entry remains available for eligible files beyond a bound.

Save independently reloads the registered catalog, validates all path components
and regular-file/size constraints, and captures current bytes into the immutable
revision. The existing limits remain 16 sources per Book, 16 participants and
8 MiB of captured source bytes total. Incomplete assignments may still be saved.
Reopening verifies the retained bytes, independent of subsequent live-file edits.
The existing filesystem capture boundary is retained; this feature does not claim
an OS-level transaction against a concurrent adversarial filesystem writer.
